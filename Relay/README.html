Discord Chat Bridge — Relay Guide

This guide is for the operator — the one person who hosts the relay, the small web service that sits between everyone's game and Discord. Players' games send their chat here; the relay throws away the duplicate copies, posts a single copy to Discord, and hands Discord replies back to the games. It is the only part that ever talks to Discord.

Players don't need any of this — point them at the player guide in the SWGCommandExtension folder instead.

Where settings go

Settings are given either as environment variables on the server (written with double underscores, like Discord__WebhookUrl) or in a private file called appsettings.Production.json next to the app (written in sections, like "Discord": { "WebhookUrl": "..." }). Both spellings below mean the same setting.

Never put real keys or tokens in appsettings.json itself — that file is part of the shared project. The private file and environment variables exist so secrets stay on the server.

The essentials

These four get the bridge going. Only the first two are needed for the basic game → Discord direction.

SettingWhat it is
Discord__WebhookUrl The Discord webhook for your bridge channel. In Discord: channel settings → Integrations → Webhooks → create one and copy its URL. This is what posts guild chat into Discord.
Relay__ApiKeys__guild A password you make up that lets players use the relay — generate one in PowerShell with [guid]::NewGuid().ToString() and hand it to your guild members; it's the key they put in their ini file. The word after ApiKeys__ is just a label for your logs. You can list more than one key, which is how you swap to a new key gradually: add the new one, let people move over, then remove the old.
Discord__BotToken A Discord bot's token — needed only for the features marked "needs the bot" below. The bot must be invited to your server and able to see the bridge channel.
Discord__ChannelId The ID number of the bridge channel (right-click the channel in Discord → Copy Channel ID; you may need Developer Mode enabled in Discord's settings).

Feature switches

Every feature beyond basic chat forwarding starts off, so an update can never change what appears in your channel by itself. Turn each on when you're ready:

SettingWhat turning it on does
Discord__Stage2Enabled Messages typed in the Discord channel are carried into guild chat in-game. Needs the bot.
Discord__AlertsEnabled World boss announcements are posted as colour-coded alert boxes instead of plain chat — see the next section. Works without the bot.
Discord__CleanupEnabled Old messages in the bridge channel are deleted after about 5 hours (pinned ones are kept), so the channel works like a live ticker rather than an archive. Needs the bot, with the Manage Messages and Read Message History permissions.
Discord__CommandsEnabled The bot answers @YourBot status in the channel with who currently has the bridge running in-game. Needs the bot, with Send Messages and Read Message History.

World boss alerts

With Discord__AlertsEnabled set to true, a chat line that starts with a recognised phrase is posted as a coloured alert box instead of plain chat. Out of the box:

  • [PvE World Boss] — green
  • [PvP World Boss] — red

To change the phrases or colours, set Discord__AlertTags: each entry is a phrase and a colour number. Colours are given as plain numbers — pick a colour in any online colour picker and use its decimal value (green is 3066993, red is 15158332). For example, in appsettings.Production.json:

"Discord": {
  "AlertsEnabled": true,
  "AlertTags": {
    "[Server]": 255,
    "[Invasion]": 15158332
  }
}

Worth knowing:

  • Setting any phrase replaces the built-in pair completely, so you can retire a phrase, not just add one.
  • Capital letters don't matter when matching.
  • If one phrase begins with another (say [Boss] and [Boss Elite]), the longer one wins.
  • A line whose phrase the relay doesn't recognise is posted as ordinary chat rather than dropped — nothing is ever lost, it just isn't dressed up.

Appearance and odds & ends

SettingNormallyWhat it does
Discord__ShowContributingClientoff Adds a small note to each Discord post naming which player's game supplied it. Purely for troubleshooting; leave off day to day.
Discord__BotUserId(blank) The bot's own ID. Leave blank — the relay looks it up by itself. A wrong value here makes the bot ignore everyone.
Discord__EmbedColor3066993 The green that guild chat used back when it was posted in a box. No longer used — kept only so switching back is easy.

Fine-tuning

Everything below already has a sensible value and can be ignored. It's listed so you know what's adjustable — change things only if you have a reason to.

Chat handling

Setting (under Relay__)NormallyWhat it controls
DedupeWindowSeconds15 How long the relay remembers a chat line so the copies arriving from every guild member's game are posted only once.
BatchIdWindowSeconds300 How long the relay remembers a delivery it has already processed, so a game retrying a slow connection can't cause a double post.
MaxLinesPerBatch50 The most chat lines accepted in one delivery from a game.
MaxLineLength512 The longest single chat line accepted, in characters.
RateLimitPermitsPerMinute600 How many requests per minute one key may make in total. The whole guild shares one key, so raise this if the guild grows very chatty.
RequireHttpsoff Refuse unencrypted connections outright. Turn on once the health page confirms the server reports encrypted connections correctly.

If Discord is briefly unreachable

SettingNormallyWhat it controls
OutboxMaxEntries200 How many undelivered posts are kept waiting for another try before the oldest is let go.
OutboxMaxAttempts10 How many tries each waiting post gets before it's given up on (with a note in the logs).
StateFilePath(automatic) Where the relay keeps its memory file — waiting posts, recent lines, who's online — so nothing is lost when the app restarts.

Discord → game delivery

SettingNormallyWhat it controls
Stage2RedeliveryTimeoutSeconds60 If the game that picked up a Discord message goes quiet, how long before the message is offered to another game.
Stage2MaxDeliveries3 Total attempts per message before it's dropped.
Stage2TtlSeconds300 A Discord message older than this is dropped rather than delivered stale.
Stage2MaxPending50 How many Discord messages may queue up waiting for a game to collect them.
Stage2MaxPerPoll5 How many messages one game is handed per check-in.
Stage2FetchCacheSeconds2.5 How long a look at the Discord channel is reused before looking again, so many players online doesn't mean many calls to Discord.

Channel tidy-up

SettingNormallyWhat it controls
CleanupMaxAgeHours5 Messages older than this are deleted (pinned ones never are).
CleanupIntervalMinutes15 The shortest gap between tidy-up passes.
CleanupMaxSingleDeletesPerSweep5 A brake on the slower one-by-one deletions that very old messages need — only relevant the first time an old channel is tidied.

Who's online, and the status bot

SettingNormallyWhat it controls
PresenceOnlineWindowSeconds180 How recently a game must have checked in to count as online.
PresenceWriteIntervalSeconds30 How often each player's "last seen" note is saved to disk (a brake on disk activity, nothing more).
PresenceRetentionDays7 How long someone who stopped playing stays on the "has the bridge installed" list.
PresenceMaxClients200 A ceiling on that list, as a safety margin.
CommandScanIntervalSeconds15 The shortest gap between checks for someone mentioning the bot.
CommandMaxAgeSeconds300 A mention older than this gets no reply — better silent than out of date.
CommandMaxRepliesPerScan3 The most replies posted per check, so the bot can't flood its own channel.
DeliveryNoticeIntervalMinutes15 The shortest gap between "nobody is in game to receive this" notices.

Keeping things moving when nobody is online

SettingNormallyWhat it controls
BackgroundTickSeconds60 How often the relay does its background round (retry waiting posts, tidy the channel, answer the bot) even with nobody in game. 0 switches the round off entirely.
SelfPingUrl(blank) A web address the relay visits once per round to keep itself awake — only needed on hosting that puts idle apps to sleep. Point it at the relay's own health page. Leave blank otherwise.

Checking it's working

Open https://<your-relay-address>/api/v1/health in a browser. It shows a page of status information: whether the webhook was picked up (configured), which features are live (stage2Configured, cleanupConfigured, commandsConfigured, alertsConfigured), how many posts are waiting for retry, and who has checked in recently. It's safe to look at — it never shows keys or tokens.
